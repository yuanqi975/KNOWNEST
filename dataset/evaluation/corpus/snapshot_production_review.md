# KNOWNEST 真实使用场景评估与整改建议

## 总体结论

当前项目更接近“功能完整的 RAG/Agent 原型”或“小规模内部试用版”。它已经具备文档上传、解析、混合检索、重排、引用、Agent 工具调用和 MCP 扩展等基础能力，但距离企业生产环境仍有明显差距。

主要短板集中在：

- 智能回答与普通 RAG 的实际链路差异不足；
- 检索质量缺少查询理解、动态召回和评估闭环；
- PostgreSQL、向量库、文件存储之间缺少一致性保障；
- Agent 仍是受限 ReAct 循环，不是完整的多步研究系统；
- 权限、密钥、上传安全和生产运维能力不足；
- 可观测性和故障诊断链路不完整。

## 1. 智能回答与普通 RAG 的差异不足

普通 RAG 和智能回答都先调用同一个 `hybrid_search` 获取 5 条结果。普通 RAG 将结果直接放入 Prompt 后调用模型；智能回答则将相同的初始证据交给 Agent。

当初始检索结果存在时，Agent 会移除 `search_knowledge_base` 和 `read_document` 工具，避免重复检索。因此，如果模型第一轮直接生成答案，两个模式实际上只是系统提示词不同，最终答案和引用很容易完全相同。

当前“智能回答”更像“带工具调用能力的 RAG”，还不是具备以下能力的 Agentic RAG：

- 查询理解和查询改写；
- 子问题拆解；
- 多轮检索和多跳推理；
- 多来源交叉验证；
- 冲突证据处理；
- 引用完整性校验；
- 明确的任务完成条件和失败恢复。

## 2. 检索链路的不足

当前检索采用 Dense + BM25 + RRF，并尝试调用 Rerank，结构清晰，但真实场景仍有以下问题。

### 2.1 缺少查询理解和查询改写

原始问题基本直接进入向量和关键词检索，没有：

- 查询改写；
- 多查询扩展；
- 同义词扩展；
- 意图识别；
- 时间、部门、文档类型等过滤条件抽取；
- 多轮对话中的独立问题重写。

类似“那份制度里这个情况怎么处理”的问题，在上下文不完整时容易召回错误内容。

### 2.2 Top K 固定且偏小

问答链路固定取 5 条结果，不适合跨章节总结、多文档比较、流程型问题以及“列出所有符合条件的项目”等任务。

建议根据问题复杂度、候选分数和上下文预算动态调整召回数量。

### 2.3 Rerank 失败时会静默降级

Rerank 没有配置凭据或调用失败时，系统会回退到 RRF 候选排序。虽然事件中有降级标记，但系统仍然可以继续提供看起来正常的答案，用户不一定意识到检索质量已下降。

生产环境应明确展示能力状态，并对关键知识库配置做启动检查或健康检查。

### 2.4 缺少检索质量评估闭环

目前缺少完整的线上和离线指标：

- Recall@K；
- MRR、NDCG；
- 引用命中率；
- 答案忠实度；
- 无答案识别准确率；
- 用户反馈和问题回放；
- 不同知识库、切片策略和模型配置的对比。

没有评估集，就无法客观判断切片、Embedding、Rerank 或 Prompt 的优化是否有效。

### 2.5 引用不等于答案可信

系统保存检索引用，但没有验证：

- 答案中的引用 ID 是否真实存在；
- 每个关键结论是否被引用支持；
- 引用片段是否与结论相关；
- 答案是否混入知识库之外的信息。

当前主要依赖 Prompt 要求模型引用，不能保证引用和答案真正一致。

## 3. 文档解析和切片能力不足

目前支持 PDF、Markdown、TXT、DOCX，但解析能力仍偏基础，企业文档场景可能遇到：

- 扫描 PDF 没有 OCR；
- 图片、截图、图表没有视觉理解；
- DOCX 复杂布局、文本框、批注、页眉页脚支持有限；
- Excel、PPT、HTML、邮件等常见格式覆盖不足；
- 表格转文本后丢失结构语义；
- 缺少文档版本管理；
- 缺少增量解析和增量索引；
- 内容 hash 尚未充分用于去重和变更检测。

真实场景中，文档解析和结构保真度往往比模型本身更直接地决定问答效果。

## 4. 索引、数据库和文件存储的一致性风险

### 4.1 PostgreSQL 与向量库不是事务一致的

chunk 元数据保存在 PostgreSQL，向量保存在 Milvus，两者没有统一事务。可能出现：

- Embedding 成功但数据库提交失败；
- 数据库删除成功但向量删除失败；
- Worker 中途崩溃；
- Milvus 暂时不可用导致部分索引缺失；
- PostgreSQL 与 Milvus 中存在孤儿数据。

目前只在部分检索路径中清理失效向量，缺少完整的对账、修复和重建机制。

### 4.2 知识库删除缺少明确的向量清理闭环

文档删除会删除对应 chunk 向量，但知识库删除路径没有形成明确的向量批量清理流程，长期运行可能残留不可见向量。

### 4.3 Milvus 失败时静默退化到进程内内存

当 Milvus 不可用且 `require_milvus` 未开启时，VectorStore 会使用进程内内存字典。该行为适合测试，不适合生产：

- 服务重启后索引丢失；
- 多进程之间数据不一致；
- 多副本部署时每个实例看到的向量不同；
- 系统可能没有明显地提示用户已降级。

### 4.4 文件存储依赖本地磁盘

上传文件保存在本地路径，不适合容器重建、多副本、跨节点 Worker、自动扩缩容和灾备。生产环境应接入对象存储或统一持久化存储。

## 5. Ingestion 和高并发能力不足

上传接口直接读取整个请求体到内存，存在以下风险：

- 大文件占用大量内存；
- 上传大小限制没有形成严格的执行闭环；
- 没有流式上传；
- 没有病毒扫描；
- 没有可靠的 MIME 和文件内容校验；
- Celery 入队失败时会回退到 API 服务线程执行，可能阻塞请求处理。

父子 chunk 关联使用逐个扫描方式，大文档下可能出现明显的性能问题。

## 6. Agent 架构仍然比较初级

当前 Agent 具备最大步骤数、工具调用数、超时、MCP 审计和隐藏思维链保护，这些设计是合理的，但仍存在以下问题。

### 6.1 没有真正的任务状态机

Agent 主要依赖模型自行决定是否调用工具，没有显式维护：

- 任务分解结果；
- 子问题状态；
- 证据覆盖率；
- 冲突证据；
- 任务完成条件；
- 失败恢复和重试策略。

模型第一轮直接回答时，Agent 会立即结束，无法保证完成了足够的研究步骤。

### 6.2 工具结果没有独立验证层

工具调用成功不代表答案正确。系统缺少事实核验、引用完整性检查、低置信度拒答、结果冲突检测和结构化输出校验。

### 6.3 上下文和成本控制不足

对话历史按最近 20 条消息读取，工具结果可能达到 20,000 字符，但没有按 token 预算做摘要、压缩和裁剪。

长对话和多轮工具调用可能导致：

- 超出模型上下文窗口；
- 增加模型成本；
- 降低回答质量；
- 触发超时。

### 6.4 文档、配置和代码存在不一致

例如文档描述的 Agent 最大推理步骤数与代码中的实际限制不一致，说明产品约束、文档和实现还没有完全统一。

## 7. 多租户和权限模型不足

当前主要是“用户拥有 Workspace，Workspace 拥有知识库”的个人工作区模型，不足以支撑完整的企业协作：

- Workspace 成员；
- 管理员、编辑者、查看者角色；
- 知识库级权限；
- 文档级权限；
- 部门和组织隔离；
- 会话共享；
- 审批、审计和 API Key 权限范围。

项目定位是企业知识工作场景，但现有权限模型更接近个人知识库产品。

## 8. 安全问题

### 8.1 默认 JWT 密钥不安全

配置存在默认的 `change-me-in-production`，如果部署时忘记覆盖，可能导致 JWT 被伪造。

### 8.2 CORS 过于宽松

当前允许所有来源、方法和请求头。生产环境应限制可信前端域名、方法和请求头。

### 8.3 上传安全不完整

应补充并强制执行：

- 文件大小限制；
- MIME 与文件签名校验；
- 病毒扫描；
- 文件名和路径安全处理；
- 磁盘配额；
- 解压炸弹和恶意文档防护。

### 8.4 需要立即检查和轮换环境凭据

仓库当前环境文件中存在疑似真实 API Key。应立即撤销并轮换，检查 Git 历史、日志和构建产物是否泄漏，并改用 Secret Manager。

## 9. 数据库迁移和生产运维能力不足

当前通过 `create_all()` 和启动时 `ALTER TABLE` 处理数据库结构变化，适合本地原型，不适合生产：

- 没有正式迁移版本；
- 无法可靠回滚；
- 多实例启动可能发生迁移冲突；
- 无法审计结构变更；
- 复杂数据迁移难以安全执行。

应引入 Alembic 或同等迁移机制，并将迁移作为独立部署步骤。

`/ready` 目前主要检查数据库查询，没有完整检查 Redis、Celery Worker、Milvus、Embedding、Rerank、LLM 和文件存储状态，可能出现“服务 ready 但实际不能问答或索引”的情况。

## 10. 可观测性不足

虽然模型中存在请求日志和 MCP 调用审计结构，但核心链路还需要补充：

- request ID 全链路贯穿；
- 解析、切片、Embedding、检索、Rerank、LLM 各阶段耗时；
- 首 token 延迟；
- Token 用量和费用；
- Prompt 和响应版本；
- 失败分类；
- 分布式 tracing；
- 用户反馈；
- 检索和答案质量回放。

否则出现答案质量下降或延迟升高时，很难判断具体故障阶段。

## 11. 前端能力表达不够准确

前端明确区分“普通 RAG”和“智能回答”，但实际链路中两者经常使用同一批检索结果，容易造成用户预期偏差。

建议明确展示：

- 是否使用向量检索；
- 是否使用关键词检索；
- 是否使用 Rerank；
- 是否调用工具；
- 本轮是否执行了多步研究；
- 答案是直接生成还是经过多轮验证；
- 当前是否处于降级状态。

## 已有的合理设计

项目已经具备一些良好基础：

- Dense + BM25 + RRF 混合检索；
- Rerank 扩展点；
- 父子 chunk；
- 来源引用和原文定位；
- Agent 步骤、工具数和超时限制；
- 不向前端暴露隐藏思维链；
- MCP 工具显式启用和调用审计；
- Celery 文档索引任务；
- 密码不以明文保存；
- 基本的用户、Workspace 和知识库隔离。

这些能力可以作为后续生产化的基础。

## 整改优先级

### P0：安全和数据可靠性

1. 立即轮换仓库环境文件中的 API Key。
2. 强制配置随机 `SECRET_KEY`，禁止使用默认值启动生产环境。
3. 限制 CORS。
4. 强制执行上传大小、类型、内容和磁盘配额检查。
5. Milvus 不可用时禁止静默退化到进程内内存。
6. 补齐知识库、文档和向量的删除、对账、重建机制。
7. 引入正式数据库迁移。

### P1：问答质量和智能链路

1. 增加查询改写、多查询召回和动态 Top K。
2. 明确 Rerank 的启用、失败和降级状态。
3. 增加无答案检测和引用一致性校验。
4. 建立离线评估集、线上反馈和问题回放。
5. 按 token 管理对话上下文、工具结果和成本。
6. 重新设计 Agent 的任务分解、多轮检索、证据验证和完成条件。

### P2：企业化能力

1. 增加 Workspace 成员和 RBAC。
2. 增加文档级权限和组织隔离。
3. 接入对象存储。
4. 增加 OCR、多模态文档和更多办公格式解析。
5. 增加文档版本管理和增量索引。
6. 建立完整监控、成本、审计和告警体系。
7. 对多进程、多副本和故障恢复进行部署验证。

## 最终判断

项目的功能面已经像一个完整产品，但生产可靠性和智能链路差异化仍处于原型阶段。当前最值得投入的方向不是继续堆叠更多工具，而是优先补齐：

1. 检索质量和评估闭环；
2. 索引、向量库和文件存储的一致性；
3. 权限、安全和密钥管理；
4. Agent 的真实多步研究能力；
5. 监控、成本和故障诊断能力。
